# CHOM — Context Harness for Obsidian Markdown

> An AI-guided proposal-questioning and reflection workflow for hackathon participants.

## Status

**All 5 core concepts working end to end:** API endpoints, database persistence, LLM-generated questions, caching, and Markdown + PDF reporting. Seed data and a test suite are also in place.

## Setup

**1. Install dependencies:**

```bash
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
```

**2. Get a free Gemini API key** from [Google AI Studio](https://aistudio.google.com/apikey) (no credit card required).

**3. Create a `.env` file** in the project root with your key:

```
GEMINI_API_KEY=your-key-here
```

**4. Start the server:**

```bash
./.venv/bin/uvicorn app.main:app --reload
```

The API is now running at `http://localhost:8000`.

## 5-minute demo path

With the server running (see Setup above), this is the fastest way to see CHOM work end to end:

1. Run the seed script: `./.venv/bin/python3 seed.py`
2. Watch the terminal output — it prints each step live: session created, questions answered, criteria added, options scored, report exported.
3. Open the exported files it created in the `Project/` folder — one `.md` and one `.pdf`, both named after the session id printed in step 2.
4. Run the command the script prints at the end (`curl localhost:8000/sessions/<id>/comparison`) to see the weighted scores that decided the winning option.

That's the whole flow — one idea in, a reasoned decision and a shareable report out — without touching any endpoint by hand. (To do it manually instead, follow "Using it — a full session, step by step" below.)

## Running the tests

```bash
./.venv/bin/python3 -m pytest tests/ -v
```

Runs in under a second — no real LLM calls are made (the LLM call is mocked), and each test uses its own isolated, temporary database.

## Using it — a full session, step by step

Each step below is one `curl` command. Save the `id` you get back from each response — you'll need it in later steps.

**1. Start a session with your idea:**

```bash
curl -X POST localhost:8000/sessions \
  -H "Content-Type: application/json" \
  -d '{"proposal": "A tool that reminds hackers to sleep"}'
```

You get back a session `id` and the first question, generated by the AI.

**2. Answer the question** (repeat up to 5 times — each answer returns the next question, until `"done": true`):

```bash
curl -X POST localhost:8000/sessions/<SESSION_ID>/answers \
  -H "Content-Type: application/json" \
  -d '{"answer": "Students during hackathon all-nighters"}'
```

**3. Define what matters to you** — add a criterion with a weight (how important it is, e.g. 1-5):

```bash
curl -X POST localhost:8000/sessions/<SESSION_ID>/criteria \
  -H "Content-Type: application/json" \
  -d '{"name": "cost", "weight": 3}'
```

Repeat for each criterion you want (e.g. "speed to build", "ease of use"). Save each criterion's `id`.

**4. Score your candidate options** against each criterion (score 1-5):

```bash
curl -X POST localhost:8000/sessions/<SESSION_ID>/options \
  -H "Content-Type: application/json" \
  -d '{"option_name": "Option A", "criterion_id": "<CRITERION_ID>", "score": 4}'
```

Repeat for every (option, criterion) pair you want scored.

**5. See which option wins:**

```bash
curl localhost:8000/sessions/<SESSION_ID>/comparison
```

Returns each option's total weighted score, highest first.

**6. Export your project brief:**

```bash
curl -X POST localhost:8000/sessions/<SESSION_ID>/export
```

Writes a Markdown file and a PDF to the `Project/` folder, containing your proposal, the full Q&A, and the option comparison — ready to keep or share.

Data survives an app restart — everything lives in `chom.db` (git-ignored).

## Example scenario

Maya is at a hackathon with a rough idea: *"a browser extension that blocks distracting sites during a coding sprint."* She doesn't know yet whether to build it as a Chrome extension, a browser-agnostic proxy, or a simple system-level app blocker — and she has three hours before the deadline to decide and start building.

She starts a CHOM session with her one-sentence idea. CHOM asks her: *"Who specifically struggles with this — you personally, or a broader group, and what happens right now when they try to focus?"* She answers. It asks a follow-up about how strict the blocking needs to be. She answers that too. After a few rounds, CHOM stops asking — it has enough to work with.

Maya then defines what actually matters to her: **speed to build** (weight 5, since she only has three hours) and **works without installing anything** (weight 4, since she wants to demo it on the judges' laptop). She scores her three candidate approaches — Chrome extension, browser proxy, system-level blocker — against both criteria. CHOM shows her the totals: the Chrome extension wins clearly, mostly because of the "works without installing anything" criterion scoring high on it (judges likely already use Chrome).

She exports the session. CHOM hands her a Markdown file and a PDF containing her original idea, every question she answered, and the full comparison — a record she can drop straight into her hackathon submission, showing not just what she built but why.

Fifteen minutes have passed. She starts coding with a decision already made and written down, instead of still debating it an hour in.

## The problem

Hackathon participants often start with an interesting idea but lack a clear problem statement, scope, technical direction, or record of why a decision was made. Unstructured planning can consume hours and still produce a project that is too broad to finish.

## What CHOM does

CHOM begins when a participant submits a project proposal in their own words. It then asks focused, bounded questions that help the participant examine assumptions, clarify constraints, identify trade-offs, and reflect on what matters most.

CHOM does **not** give a definitive answer or select an architecture for the participant. It helps them compare a small number of options against criteria they have weighted themselves, then documents their approved decision in Obsidian-compatible Markdown and a concise PDF decision report.

```text
Project proposal
  → focused questions
  → participant reflections and criteria weights
  → transparent option comparison
  → participant selects a direction
  → Markdown project folder + PDF decision report
```

## Who it is for

- Individual hackathon participants.
- Small hackathon teams deciding what to build.
- Students and early-stage builders who want a durable record of their project reasoning.

## Non-negotiables

- The participant makes the final decision.
- The LLM has one narrow role: ask the next focused question and provide reflective option notes.
- AI output must be validated before it is shown.
- Final artifacts are based on user-confirmed answers and selections.
- Scores must be traceable to participant-defined criteria and weights.
- The application must remain simple to run locally.

## Out of scope

- Building the participant's application.
- Autonomous architecture selection or unrestricted agents.
- Web scraping, RAG, vector databases, or third-party workflow automation.
- Docker as a requirement, n8n, team collaboration features, or external syncing.

## Technical approach

- **API:** FastAPI
- **Persistence:** SQLite
- **Validation:** Pydantic
- **AI:** one LLM-provider adapter with structured responses
- **Caching:** session-state hashes for unchanged questions or assessments
- **Artifacts:** template-based Markdown plus PDF reporting
- **Testing:** pytest with seeded demo sessions

## How each concept works, in plain terms

1. **API Endpoints** are set of routes for CHOM to a client (website, an app, or in our testing, simple commands) to knock on to make something happen like creating new sessions, submitting an answer, add criterion. It's how it makes each system or concept communicate with each other.

2. **Database**, this is where CHOM's learnings are permanently saved. Every ideas, questions, answers, criteria scores, weight are saved for each option in a file chom.db

3. **LLM Integration**, is how CHOM speaks and guides the AI model to speak. So when the AI generates the question, it makes sure to check if the question is valid before showing it.

4. **Caching Logic**, makes CHOM remember conversations and relates them to direct LLM, so when you ask it a question it tries to check whether it has already generated an answer to exactly the same question so that it is able to reuse the idea.

5. **Reporting**, CHOM takes everything that was saved in the database from: proposal, Q&A, option comparison, and turns them into 2 finished documents: Markdown file, and PDF written inside the Project/ folder.

CHOM aims to help a participant turn an initial hackathon proposal into a user-refined, technically reasoned project brief in about **15 minutes**, rather than several hours of unstructured planning. This claim will be tested using the same sample idea in both workflows.

## Future ideas

The capstone core is a raw API — every action is a `curl` command. That's intentional for now (see "Realistic scope" in the capstone brief: no UI required), but it's not how CHOM is meant to be used long-term. Planned, after the capstone submission:

- A simple web front end, so a participant can go through a session by clicking instead of scripting requests by hand.
- A CLI (`chom start "my idea"`) as a lighter-weight alternative to a full UI.
- Session resuming from the front end (the API already supports it — `GET /sessions/{id}` — just no client for it yet).
- Support for swapping the LLM provider (e.g. Claude) without code changes, likely via an environment variable, building on the fact that `app/llm.py` already isolates all Gemini-specific code behind one interface.
- Optional API key: letting a user bring their own LLM provider key at request time instead of the one fixed key set in `.env`, so multiple people could use a shared deployment of CHOM without sharing one account's quota.

## Security and data handling

No secrets belong in the repository. API keys and configuration will be supplied through environment variables and excluded through `.gitignore`. Demo data will be seeded and will not use other people's personal data.
